# Architecture

hlwgpu is the HashLink adapter and distribution layer for xgpu. The public
Haxe API is generated by xgpu; hlwgpu supplies the ABI carriers, native
library, browser side module, release bundles, and HXSL compiler.

## Ownership

| Layer | Owner | Responsibility |
|---|---|---|
| API and WebIDL model | xgpu | Portable WebGPU surface, native extensions, enum values, and generated bindings |
| GPU implementation | xgpu backend | wgpu resource tables and native operations |
| HashLink adapter | hlwgpu | Haxe externs, HashLink values, Future conversion, native primitive exports |
| Browser transport | xgpu + hlwgpu | Shared-memory command wire, generated WebGPU agent, Ash harness modules |
| Typed shaders | hlwgpu | HXSL checking, linking, layout calculation, and WGSL emission |

The generated files under `haxe/gpu` are committed so a source checkout and a
release expose the same API. Their header identifies xgpu-bindgen as the
source; changes belong in xgpu's IDL, declaration, or generator.

## Native path

`xgpu.hdll` embeds xgpu's wgpu backend. Generated HashLink primitives convert
Haxe values to xgpu's runtime-neutral Rust model and call that backend. The
library selects the platform backend compiled into its release: Metal, D3D12,
Vulkan, or OpenGL ES.

GPU objects cross as compact generational integer handles. The handle records
a resource kind, so passing a texture where a buffer is required fails before
backend code sees the value. Descriptor records cross as HashLink native
abstracts. Strings and byte buffers use HashLink's own allocations and rooting
rules rather than a parallel plugin heap.

## Async seam

The IDL's Promise-returning operations become `ash.Future<T>`. The adapter
creates and settles the Future through `hlp_future_*` symbols supplied by the
program runtime. Native callbacks therefore complete an object owned by the
same HashLink heap as the caller; hlwgpu does not link a second runtime.

This ABI is built into Ash. Other HashLink hosts can support the same API by
providing the Ash Future ABI.

## Browser path

The browser build is `xgpu.wasm`, a threaded WASI position-independent side
module. It contains the generated HashLink model and guest encoder, while
WebGPU itself runs in JavaScript through `gpu-agent.mjs`.

The runtime owns the page, dylink relocation, shared memory, table, Worker,
canvas policy, and isolation headers. Ash's supplied `gpu.mjs` and
`gpu-worker.mjs` implement that harness. `hlwgpu.js` is a small neutral entry
that exposes the side-module URL to another runtime's loader.

The mailbox is shared across languages and runtimes. A WebGPU call is encoded
into shared memory, the browser agent performs it, and `ash_host_watch` wakes
the suspended fiber when the completion word changes. Native-only operations
that cannot run in a browser raise a runtime error through the same generated
API.

## Resource lifetime

GPU memory is released explicitly through `destroy()`. A GPU allocation may
be megabytes while its Haxe handle is one integer, so language-heap pressure
cannot decide when driver memory should be reclaimed. Destroying a handle is
idempotent and advances its generation, which turns later stale uses into an
error.

HashLink-managed descriptors follow normal GC lifetime. Values retained by an
asynchronous operation are rooted through the adapter until completion.

## HXSL

`hlwgpu.hxsl.Shader` runs as a Haxe build macro. It checks HXSL, links imports
and framework extensions, separates shader stages, removes dead code, emits
WGSL, and adds constants describing the resulting bind groups and memory
layout. The output is ordinary WGSL passed to `GpuDevice.createShader()` or a
shader-module descriptor.

## Surfaces

hlwgpu does not own a window system. Native surface creation consumes raw
window and display handles supplied by the application or a window library.
`crates/hlwindow` exists for repository tests only. Browser presentation uses
the canvas owned by the runtime harness.

## Legacy native implementation

`wgpu.api`, `src/imp.rs`, and `hl_native_gen` predate xgpu. They remain inside
the native library while compatibility code is retired, but they no longer
define the public Haxe API or browser implementation. The canonical API,
WebIDL snapshot, enum catalog, and reusable backend all live in xgpu.

## Validation

CI checks the Rust workspace, type-checks the generated `gpu` package, runs
the HXSL compiler test, and verifies that a build does not change committed
generated files. Release CI additionally builds desktop and mobile artifacts,
links the threaded Wasm side module, checks every generated HashLink primitive
is exported, and parses each JavaScript module.
